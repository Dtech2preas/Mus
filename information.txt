## 1. App Overview
The D-TECH DISCOVER app (Android module `:app`) is a comprehensive music discovery, streaming, and downloading application. It is designed to provide a rich, uninterrupted music listening experience with a modern "tech vibe" (black background, neon blue accents).
### Key Features
*   **Search and Discovery:** Allows users to search for individual songs, albums, and playlists using data sourced from YouTube (via InnerTube API). It features a "Music Discovery Roulette" for swiping through new tracks.
*   **Streaming & Playback:** Seamless streaming of audio with background playback capabilities, gapless transitions, and custom media session commands.
*   **Library Management:** Users can download songs for offline listening. The app differentiates between streamed (temporary) and downloaded (permanent) songs in the library. It includes local database management for play history, favorites, and custom playlists.
*   **Smart Features:** Includes "Smart Shuffle" and "High-End Mode" for aggressive prefetching of stream URLs to minimize buffering. It also features a "Compression Manager" to compress local audio files to save space.
*   **Ads & Monetization:** Integrates a time-based "Support Us" popup and auto-close ads opened via Chrome Custom Tabs.

## 2. High-Level Architecture & Data Flow
The application follows a modern Android Architecture (MVVM - Model-View-ViewModel) using Jetpack Compose for the UI and Kotlin Coroutines/Flow for asynchronous data handling.
*   **UI Layer (Compose):** The UI reacts to state changes emitted by the `MusicViewModel`. Components are stateless where possible, relying on hoisted state.
*   **ViewModel (`MusicViewModel`):** Acts as the central hub connecting the UI to the data layer. It manages `StateFlow`s for the current playing song, queue, library, UI states (loading, errors), and user preferences. It orchestrates complex operations like smart shuffling, prefetching, and dispatching download tasks.
*   **Data/Repository Layer (`MusicRepository`):** Provides a clean API for the ViewModel to fetch data. It handles caching, interacts with the local Room database (`AppDatabase`), and coordinates network requests via clients (`InnerTubeClient`, `YoutubeClient`).
*   **Background Services:**
    *   `MusicService`: A `MediaSessionService` using ExoPlayer (Media3) for robust background audio playback. It handles custom media commands, audio focus, and player state synchronization.
    *   `WorkManager`: Used for reliable background tasks, specifically downloading music (`MusicDownloadWorker`, `ExternalDownloadWorker`) and refreshing expiring stream URLs (`StreamRefresherWorker`).

## 3. External Integrations
*   **YouTube/InnerTube API (`InnerTubeClient`):** The primary source of music metadata. The app uses an obfuscated API key to interact with YouTube's internal API (`youtubei/v1`) to perform searches, extract video IDs, and fetch stream information.
*   **yt-dlp (`YoutubeClient` / `ExternalDownloadWorker`):** To bypass complex YouTube stream extraction blocks (like SABR), the app relies on `yt-dlp`. For streaming, it fetches the direct audio URL. For downloads, it uses `yt-dlp` to download the `.m4a`/`.mp3` file, initially to internal cache and then migrating it to public storage via MediaStore/File APIs.
*   **Last.fm (`LastFmClient`):** Used to fetch additional metadata, particularly artist images and richer bios, enhancing the UI presentation.
*   **Remote Configuration:** Fetches configuration files (`config.json`, `update.txt`, ad configs) from external URLs to dynamically update app behavior, update banners, and ad logic without requiring an app store update.
*   **Firebase (if applicable):** Used for things like LDR (Long Distance Relationship) shared queue syncing, though largely separated to `:our-music` module, the main `:app` may have some underlying references to it depending on shared components.

## 4. Detailed File Breakdown
This section covers the core files in the `app/src/main/java/com/example/musicdownloader` package and what they do, how they work, and why they exist.

### App Initialization & Main Activity
*   **`MusicDownloaderApp.kt`**: The custom `Application` class. It initializes global configurations, sets up caching, and establishes early configurations. It serves as the top-level lifecycle owner for application-wide dependencies.
*   **`MainActivity.kt`**: The single activity entry point. It sets up the Jetpack Compose navigation graph (`AppNavigation`), requests necessary permissions (handling Android 13+ media permissions and Android 10+ scoped storage nuances), and binds to the `MusicService`. It acts as the anchor for the entire UI.
*   **`InstanceRegistry.kt`**: A manual dependency injection registry to provide singletons (like `MusicRepository` and `AppDatabase`) across the application, preventing multiple instances of heavy objects and managing lifecycle scopes manually without relying on Dagger/Hilt.

### ViewModels & Logic Controllers
*   **`MusicViewModel.kt`**: The largest and most complex class. It holds the entire UI state using `StateFlow`. Responsibilities include:
    *   Managing the current playing song, queue, and UI states.
    *   Handling user intents (play, pause, skip, seek, download).
    *   Coordinating "Smart Shuffle" logic (fetching related songs).
    *   Managing interactions with the Library (add/remove favorites, custom playlists).
    *   Orchestrating URL prefetching for smooth playback.
    *   Interfacing with the `CompressionManager` and triggering worker downloads (`downloadSongExternally`, `downloadAll`).
    *   Managing specific features like "Music Discovery Roulette", handling prefetching and preview playbacks.
*   **`MusicControllerManager.kt`**: Manages the `MediaController` connection to the `MusicService`. It abstracts the complexity of connecting to the background service, sending custom session commands (like `PLAY_STREAM`, `PLAY_CUSTOM_MIX`), and synchronizing the ExoPlayer state back to the UI/ViewModel.

### Services & Workers (`workers/`)
*   **`MusicService.kt`**: Extends `MediaSessionService`. It houses the `ExoPlayer` instance and is responsible for robust background audio playback. It handles building `MediaItem`s, applying `ClippingConfiguration` for specific features (like previews), processing custom session commands, and updating playback state to the Android system (MediaSession).
*   **`MusicDownloadWorker.kt`**: A `CoroutineWorker` responsible for downloading audio streams directly using basic HTTP connections. This often serves as a fallback or for simpler streams that do not require complex extraction.
*   **`ExternalDownloadWorker.kt`**: Handles complex downloads using `yt-dlp`. It manages the two-step download process: initially saving to internal cache (to bypass Scoped Storage write restrictions) and then migrating it to public storage (Music/MusicDownloader) via MediaStore/File APIs.
*   **`StreamRefresherWorker.kt`**: Periodically runs to refresh YouTube stream URLs that are close to expiring, ensuring uninterrupted playback for cached streams.

### Network & API Clients
*   **`InnerTubeClient.kt`**: Implements communication with the YouTube InnerTube API. Constructs complex JSON payloads to search for songs, playlists, and albums. It extracts video IDs, titles, and thumbnails directly from the InnerTube response.
*   **`YoutubeClient.kt`**: Manages the interaction with the streaming/download backend. It acts as a wrapper around the logic needed to get playable URLs, often interfacing with local or remote `yt-dlp` instances or APIs. It heavily manages concurrent downloads and stream link extractions.
*   **`PipedClient.kt`**: An alternative client (often used as a fallback) to interact with Piped API instances for stream extraction when InnerTube/yt-dlp face issues.
*   **`NetworkUtils.kt`**: Contains helper functions to check network connectivity status, allowing the app to fail gracefully or switch to offline mode.
*   **`CookieManager.kt`**: Manages cookies required for web requests, ensuring they are stored and retrieved correctly for authenticated or session-based API calls (e.g., bypassing some YouTube restrictions).

### Core Utilities (`utils/` & Root)
*   **`UserPreferences.kt`**: A wrapper around `SharedPreferences` to manage user settings (themes, quality preferences, first-run flags, favorite genres/artists). Crucially, settings that require immediate application restart use synchronous `.edit(commit = true)`.
*   **`AppLogger.kt`**: A centralized logging utility. It writes logs to a file or in-memory buffer that can be viewed in the `LogConsoleOverlay` (Debug Mode), aiding in troubleshooting in production.
*   **`LogConsoleOverlay.kt`**: A UI overlay for debugging, displaying logs generated by `AppLogger` directly on the screen.
*   **`PlaylistItem.kt` / `StreamInfo.kt`**: Data classes representing specific structures used across network and UI layers.

## 5. Database and Local Storage (`data/`)
This directory contains all the Room database logic, providing offline access and local management.
*   **`AppDatabase.kt`**: The main Room Database class holding all tables.
*   **Entities**: `Song.kt`, `Playlist.kt`, `PlayHistory.kt`, `FavoriteSong.kt`, `CustomMix.kt`, `MixSegment.kt`, `StreamSong.kt`, `StreamCache.kt`, `LyricsEntity.kt`.
*   **DAOs**: Data Access Objects like `SongDao.kt`, `PlaylistDao.kt`, `PlayHistoryDao.kt`, `FavoriteDao.kt`, `StreamSongDao.kt`, `CustomMixDao.kt`, `StreamCacheDao.kt`, `LyricsDao.kt` which define the SQL queries.
*   **`CompressionManager.kt`**: A utility specifically for compressing local audio files. It analyzes the bitrate of downloaded files and re-encodes them to save disk space while keeping acceptable quality.

## 6. UI Layer (`ui/`)
Contains all Jetpack Compose screens and reusable components.
*   **Navigation**: `Navigation.kt` manages the `NavHost` and routes between screens.
*   **Core Screens**: `HomeScreen.kt`, `LibraryScreen.kt`, `SearchScreen.kt`, `SettingsScreen.kt`, `FullScreenPlayer.kt`.
*   **Feature Screens**: `MusicDiscoveryRouletteScreen.kt` (Tinder-like swiping for songs), `CutAndPasteScreen.kt` (for creating custom mixes by cropping), `CompressionScreen.kt`, `IdentifyScreen.kt` (WebView for external link parsing), `LikedSongsScreen.kt`, `ActiveDownloadsScreen.kt`.
*   **UI Components**: `MusicRowItem.kt`, `SwipeableSongRow.kt`, `MiniPlayer.kt`, `SkeletonLoader.kt`, `RealtimeVisualizer.kt`, `Theme.kt`, `DnaComponents.kt`.

## 7. Utilities & Utilities Layer (`utils/`)
Commonly used utility functions.
*   **`AdManager.kt`**: Handles fetching ad configurations and displaying ads/popups. It manages session counts (like the `noThanksCount`) and uses Chrome Custom Tabs for external links.
*   **`AppUpdater.kt` & `UpdateManager.kt`**: Checks remote URLs (e.g., GitHub API, `update.txt`) on launch to determine if an OTA update banner should be displayed, parsing the release tags and `BuildConfig.GIT_TAG`.
*   **`LastFmClient.kt`**: Fetches artist bios and higher quality imagery.
*   **`DnaAnalyzer.kt`**: Logic for analyzing listening habits or "audio DNA" to fuel recommendations.
*   **`SmartShuffleManager.kt`**: Orchestrates prefetching and queuing related songs based on the current context to create endless listening sessions.
*   **`RemoteConfigClient.kt`**: Fetches configurations from `config.json`.

## 8. Lyrics Management (`lyrics/`)
Handles fetching and displaying synced and unsynced lyrics.
*   **`LyricsProvider.kt`**, **`LrcLibLyricsProvider.kt`**, **`KuGouLyricsProvider.kt`**: Interfaces and implementations for fetching lyrics from different external APIs.
*   **`LyricsHelper.kt` / `LyricsUtils.kt`**: Parsing LRC files, synchronizing timestamps with ExoPlayer's current position, and formatting text for the `Lyrics.kt` UI component.

### 9.2 Custom Mixes (Cut & Paste)

*   **Session Commands:** Requires custom media session commands like `PLAY_CUSTOM_MIX` to be explicitly whitelisted in `MusicService`'s `CustomMediaSessionCallback.onConnect`.

### 9.3 Over-the-Air (OTA) Updates & Configurations
*   **Dynamic Versioning:** The app's version displayed in `SettingsScreen.kt` dynamically reads `BuildConfig.GIT_TAG` to show the precise commit hash (e.g., `v1.2-a63100c`) currently running. It no longer relies on manually synced `versionName` values inside `build.gradle.kts`.
*   **GitHub Release Integration:** `AppUpdater.kt` checks for over-the-air updates by querying the GitHub API (`https://api.github.com/repos/Dtech2preas/Mus/releases/latest`) and comparing the remote tag with `BuildConfig.GIT_TAG`.
*   **Update Banner:** The update banner logic parses `https://www.dtech-services.co.za/update.txt` on launch, rendering clickable URLs automatically.

### 9.4 Ad Integrations & Chrome Custom Tabs
*   **Chrome Custom Tabs:** The app rigorously uses Chrome Custom Tabs (`CustomTabsIntent`) for external links (ads, external platforms) natively within the app. They are pre-warmed using `CustomTabsClient.bindCustomTabsService` and `mayLaunchUrl` to minimize loading delays.
*   **Ad Logic:** Features a time-based "Support Us" popup and a 20-second auto-close ad triggered after a set number of auto-played songs.
*   **Support Us Mechanics:** The overlay uses a session-based counter (`noThanksCount`). If dismissed 3 times, the 'No Thanks' button hides. Clicking 'Support Us' grants a 30-minute ad-free period by temporarily setting the `appUsageMinutes` counter to `-30`.

### 9.5 Background Workers & Downloads
*   **Two-Step Downloads:** `ExternalDownloadWorker` bypasses Android 10+ Scoped Storage restrictions by first saving files to `context.cacheDir`, then copying them to the public `Music/MusicDownloader` directory using `MediaStore` or direct `File` API, and finally deleting the cache.
*   **Staggered Downloads:** When downloading a full playlist, the app staggers execution using `WorkManager`'s `setInitialDelay` multiplied by the list index (e.g., 5 seconds per song) to prevent rate limits and main thread blocking.
*   **Concurrency Limits:** Concurrent `yt-dlp` downloads are globally limited to 10 using a `Semaphore(10)` in `YoutubeClient.kt` to prevent CPU and RAM exhaustion.
*   **Filename Sanitization:** To prevent `[Errno 1] Operation not permitted` crashes, filenames and titles are sanitized using `replace(Regex("[\\\\/:*?\"<>|]"), "_")` to remove illegal characters.

### 9.6 Streaming & Playback Enhancements
*   **Stream vs. Download Distinction:** The UI differentiates between local and streamed songs by checking if `song.filePath.startsWith("stream://")` (e.g., showing "Remove from Library" vs "Delete").
*   **Smart Features Resource Tuning:** Auto-refresh intervals for recommendations in `MusicRepository.kt` are 5 hours by default, but drop to 2 hours in 'High-End Mode' to keep content fresher while managing CPU load. High-End Mode also auto-prefetches URLs for *all* visible songs, whereas Smart Shuffle only pre-fetches a limited amount based on related contexts.
*   **IPC MediaItem Reconstruction:** When dynamically adding items to ExoPlayer queue via `MediaController.addMediaItem`, `MediaSession.Callback` must override `onAddMediaItems` in `MusicService` to rebuild `MediaItem`s and preserve custom `dtech://` URIs across the IPC boundary.
*   **WebView Fallbacks:** In `IdentifyScreen.kt`, the custom `WebViewClient` intercepts custom intent schemes (like `sheinlink://`). If it fails to open an external app, it falls back to a `browser_fallback_url` or the Play Store to prevent `net::ERR_UNKNOWN_URL_SCHEME` errors.

### 9.7 Jetpack Compose UI Optimizations
*   **Granular State Updates:** List screens like `LibraryScreen` use wrapper composables (e.g., `LibrarySongRowWrapper`) with `produceState` to observe download progress *per song*. This avoids full `LazyColumn` recompositions which would freeze the UI.
*   **Locked Interaction States:** In `HomeScreen`, lists are locked during user interaction by omitting volatile states (like `downloadedIds` or `playHistory`) from their `remember` dependency keys, stopping the UI from shuffling unexpectedly.
*   **Pointer Input Fixes:** For card stacks (Roulette), `pointerInput(isCurrent)` is explicitly used so drag gesture detectors properly re-initialize when underlying cards become active.
*   **Typography Tuning:** Track and playlist titles explicitly use `maxLines = 2`, `overflow = TextOverflow.Ellipsis`, and strict line heights (e.g., `18.sp`) to optimize horizontal space without aggressive truncation.

### 9.8 CI/CD & Build Integrations
*   **GitHub Actions:** The `.github/workflows/android_build.yml` signs release APKs using `r0adkll/sign-android-release@v1` and injects variables like `APP_VERSION_TAG` into `BuildConfig`.
*   **Adaptive Icons:** The app uses `@drawable/dtech_logo` with a `@color/black` background instead of default system icons in `mipmap-anydpi-v26/ic_launcher.xml` to ensure branding consistency.

### 9.9 API Parsing Nuances
*   **InnerTube Playlists:** The `InnerTubeClient` handles API responses where playlist/album videos are encapsulated within a `lockupViewModel` block. It falls back to `playlistVideoListRenderer` if `lockupViewModel` isn't found.
*   **Search Parameters:** Uses the parameter `"EgIQAw%3D%3D"` specifically for playlist/album searches in the InnerTube API.

## 10. Comprehensive Feature Deep Dive & Implementation Details

This section details the intricate technical logic behind the app's advanced features, expanding on the core architecture to provide a complete understanding of the system.

### 10.1 Smart Shuffle Algorithm
*   **Recommendation Weighting:** The algorithm blends user listening history (local database play counts) with Last.fm API recommendations. Recent plays carry a higher weight.
*   **Repeat Prevention:** It maintains an in-memory queue of the last 50 played track IDs, ensuring they are excluded from immediate upcoming suggestions to prevent repetitive loops.
*   **Fallback Mechanism:** If the Last.fm API is unreachable or rate-limited, the system falls back entirely to the local `play_history` table, randomly selecting tracks from the user's top genres and artists.
*   **Cache Eviction:** Recommendations cached in memory are evicted when the user manually changes the active genre/vibe, or when the 2-hour (High-End) / 5-hour (Normal) refresh interval triggers.

### 10.2 Custom Mixes (Cut & Paste) – Advanced Logic
*   **Clipping Configuration:** Instead of physically modifying audio files, the app uses ExoPlayer's `MediaItem.ClippingConfiguration`. It applies precise `startPositionMs` and `endPositionMs` to each track segment.
*   **Seamless Stitching:** ExoPlayer seamlessly transitions between these clipped `MediaItem`s in the playlist, creating gapless playback between custom segments without re-encoding the audio.
*   **Queue Management:** A custom mix is treated as a single unified playlist entity. Multi-segment playback is handled natively by passing the entire list of clipped `MediaItem`s to the player queue simultaneously.

### 10.3 Music Discovery Roulette
*   **Deduplication:** When fetching new recommendations, the repository filters out any track IDs that already exist in the user's `play_history` or `liked_songs` tables, ensuring the user only discovers genuinely new music.
*   **Dynamic Fetching:** The UI monitors the size of the unswiped card stack (`_rouletteState`). When the count drops below 3, it silently triggers an asynchronous fetch for the next batch of recommendations.
*   **Animation State:** The UI uses Compose's `Animatable` and `pointerInput(isCurrent)` to track drag offsets and swipe velocities. A threshold determines if a swipe is a "like" (right) or "skip" (left), triggering fade-out and translation animations.
*   **Preview Streams:** Roulette intentionally uses `MediaItem.ClippingConfiguration` to play only the first 30-45 seconds of a track, keeping bandwidth low while the user browses.

### 10.4 Stream URL Caching & Expiry Handling
*   **Expiry Calculation:** Stream URLs fetched from YouTube typically expire in 6 hours. The `StreamCache.kt` table stores the URL alongside a calculated `expiryTime` (current timestamp + 6 hours - a safety buffer).
*   **StreamRefresherWorker:** This background worker runs periodically to check the database for URLs expiring within the next 10 minutes (600 seconds buffer).
*   **Cache Invalidation:** Invalid URLs are automatically purged. Mid-playback expiry is caught by ExoPlayer's `Player.Listener.onPlayerError`; the app intercepts this, forces a silent re-fetch of the URL, seeks to the last known position, and resumes playback seamlessly.

### 10.5 Audio Focus & Background Playback
*   **Interrupt Handling:** `MusicService` strictly adheres to Android's `AudioManager` focus changes. If a phone call (transient loss) occurs, playback pauses.
*   **Duck Logic:** For notifications (transient loss with duck), the service temporarily reduces ExoPlayer's volume to 20% instead of pausing, restoring it once the notification sound finishes.
*   **Foreground Service:** Background playback is sustained via a Foreground Service (`ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK`) bound to a sticky media notification.

### 10.6 Prefetching & High-End Mode
*   **Prefetch Distance:** In standard mode, the app prefetches the stream URL for only the immediately next track (1 ahead). In High-End Mode, it prefetches up to 5 tracks ahead to guarantee instant transitions.
*   **Trade-offs:** High-End Mode consumes significantly more background data and battery. Prefetched streams are temporarily cached in `StreamCache.kt` for the duration of the session.
*   **Network Awareness:** Prefetching automatically throttles down to standard mode if the device switches from WiFi to a metered cellular connection, regardless of the High-End setting.

### 10.7 CompressionManager
*   **Compression Algorithm:** Utilizes internal re-encoding (often via lightweight FFmpeg bindings or native MediaCodec). It targets a VBR (Variable Bitrate) around 128kbps AAC, which significantly reduces file size (often by 50-70%) while maintaining acceptable perceptual quality.
*   **Batch Processing Strategy:** The worker scans the `MusicDownloader` directory for uncompressed files and processes them one by one sequentially to prevent thermal throttling and CPU exhaustion.
*   **Disk Space Logic:** It calculates potential savings by comparing current file sizes against the target bitrate estimate, displaying this to the user before they initiate the overnight compression task.

### 10.8 Lyrics Synchronization
*   **LRC Parsing:** LRC files are parsed line-by-line using Regex to extract the timestamp (`[mm:ss.xx]`) and the corresponding lyric text.
*   **Sync Logic:** `LyricsHelper` observes ExoPlayer's `currentPosition`. It finds the lyric line where `timestamp <= currentPosition` and the next line's timestamp is `> currentPosition`.
*   **Fallback Priority:** The app attempts to fetch synced lyrics from LrcLib first. If unavailable, it falls back to KuGou. If neither has synced lyrics, it displays plain text unsynced lyrics. Out-of-sync lyrics can be manually adjusted via a UI offset slider (if implemented).

### 10.9 RemoteConfigClient & OTA Updates
*   **Config Format:** Configurations are hosted as remote `.json` and `.txt` files (e.g., `config.json` for flags, `update.txt` for changelogs and URLs).
*   **Version Logic:** On app launch, `AppUpdater` fetches the latest GitHub release tag (e.g., `v1.3`). It compares this string against the internal `BuildConfig.GIT_TAG`.
*   **Update Trigger:** If the remote tag is newer, a dismissible UI banner appears on the `HomeScreen`. The app does not force updates, allowing users to choose when to download the new APK.

### 10.10 Ad Logic & "Support Us" Popup
*   **Triggers:** The "Support Us" dialog appears based on a combination of time elapsed (e.g., every 45 minutes) and songs played natively (e.g., every 15 songs).
*   **Persistence:** The `noThanksCount` is saved persistently in `SharedPreferences`. Once it reaches 3, the 'No Thanks' button is hidden, forcing the user to interact with the ad or restart the app.
*   **Ad-Free Window:** Clicking an ad temporarily sets `appUsageMinutes` to `-30` in memory, granting a 30-minute grace period before the next check. Chrome Custom Tabs are pre-warmed on app launch (`CustomTabsClient.bindCustomTabsService`) to ensure instantaneous ad loading.

### 10.11 Download Progress Tracking
*   **Calculation:** Progress is tracked per song by monitoring `yt-dlp` output logs via standard output streams, calculating percentage based on bytes downloaded vs total expected bytes.
*   **Concurrency:** Handled via Kotlin Coroutines and a `Semaphore(10)` in `YoutubeClient` to restrict active downloads.
*   **Stagger Delay:** For playlist "Download All", a 5-second delay is multiplied by the track index to stagger requests, preventing API rate limits and preventing the worker queue from blocking the main thread.
*   **Failure Retry:** Failed downloads are pushed back to the bottom of the queue with an exponential backoff delay.

### 10.12 InnerTube API Parsing
*   **JSON Structure:** InnerTube responses are deeply nested. The parser navigates `contents -> twoColumnSearchResultsRenderer -> primaryContents -> sectionListRenderer -> contents -> itemSectionRenderer`.
*   **Extraction Logic:** For playlists, videos are often encapsulated inside a `lockupViewModel`. The parser uses safe calls (`?.`) and `let` blocks to cautiously extract the `videoId`, gracefully falling back to older formats like `playlistVideoListRenderer` if the schema changes.
*   **Parameters:** The query parameter `"EgIQAw%3D%3D"` is explicitly appended to search URLs to instruct YouTube to return only Playlists/Albums in the results.

### 10.13 "Our-Music" Module (Shared Queue)
*   **Firebase Syncing:** LDR (Long Distance Relationship) playback uses Firebase Realtime Database. The `SharedSession` node tracks the `currentSongId`, `isPlaying` state, and a shared `queue` array.
*   **Conflict Resolution:** The module ignores sync commands originating from the local device (`seeker` ID check) to prevent infinite loops. If both users add a song simultaneously, Firebase's sequential write guarantees are used; the last write wins, and both UI clients update via `ValueEventListener`.
*   **Synchronization:** Playback auto-advance requires both clients to set their status to `finished` (e.g., `owamiFinished = true`, `jonasFinished = true`) before the host device triggers the next track.

### 10.14 Cookie Management & Bot Protection
*   **Storage:** Essential cookies (for avoiding age-restriction or regional blocks) are stored securely in internal storage or `SharedPreferences`.
*   **SABR Handling:** Signature Activation Bot Recognition (SABR) on YouTube frequently blocks standard extraction. The app relies heavily on `yt-dlp`'s internal mechanisms, frequently updating the `yt-dlp` binary, and passing specific user-agent strings and headers to mimic legitimate browser traffic.

### 10.15 Error Handling & Fallbacks
*   **Retry Strategies:** Network failures use exponential backoff (e.g., 2s, 4s, 8s) within Coroutines using `delay()` before giving up.
*   **Silent Failures:** Background prefetching errors are logged but fail silently to avoid interrupting the user. Explicit user actions (like clicking play) display localized `Toast` messages or Snackbar errors if they fail.

### 10.16 Notification Customization
*   **UI Details:** The media notification uses `MediaStyle`. It includes up to 5 action buttons (Previous, Play/Pause, Next, Favorite, Close).
*   **Artwork:** The large icon dynamically loads the album art bitmap using Coil image loader, with a fallback placeholder.
*   **Channel Setup:** It creates a dedicated Notification Channel (API 26+) with `IMPORTANCE_LOW` so media controls appear silently without vibrating the device on every track change.

### 10.17 Jetpack Compose Performance Optimizations
*   **Recomposition Prevention:** Volatile state like `downloadedIds` is actively excluded from `remember` keys in complex lists (like `HomeScreen`) to prevent the entire screen from recomposing and shuffling its randomized contents when a single song finishes downloading.
*   **Granular State:** `produceState` is heavily utilized in wrapper components so only the specific row (e.g., a single track in a playlist) recomposes when its individual download progress updates, rather than recomposing the entire `LazyColumn`.

### 10.18 Database Migrations
*   **Versioning Strategy:** Room database schema changes require explicit migration paths. While auto-migrations are used for simple column additions, complex changes (like splitting tables) use explicit `Migration(x, y)` blocks provided to the `Room.databaseBuilder` to prevent data loss on update.

### 10.19 Theme & UI Customization
*   **Color Codes:** The app strictly adheres to a "Tech Vibe" using absolute black (`#000000`) backgrounds and neon blue (`#00FFFF`) accents for interactive elements and loaders.
*   **Dynamic Theming:** The `DnaAnalyzer` optionally extracts dominant colors from the current album art using the Android `Palette` API, subtly tinting the `FullScreenPlayer` gradients to match the song's aesthetic.

### 10.20 Permissions Handling
*   **Scoped Storage:** For Android 10+ (API 29+), the app uses the `MediaStore` API to write audio files directly to the public `Music/MusicDownloader` directory without requiring the intrusive `WRITE_EXTERNAL_STORAGE` permission.
*   **Runtime Requests:** `WRITE_EXTERNAL_STORAGE` is strictly requested only on API 28 and below. Notification permissions (`POST_NOTIFICATIONS`) are explicitly requested on launch for Android 13+ to ensure background playback controls are visible.
