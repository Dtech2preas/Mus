# Over-The-Air (OTA) Update Logic & CI/CD Setup

This document details how the in-app update mechanism and the automated GitHub Actions CI/CD release process are implemented. You can use this guide to replicate this functionality in other Android app repositories.

## 1. AppUpdater.kt - Checking for Updates
The core logic for checking updates relies on comparing the app's current `versionName` (defined in `build.gradle.kts`) against the latest release tag on GitHub.

### How it works:
- **API Call**: The app makes a GET request to the GitHub API: `https://api.github.com/repos/<OWNER>/<REPO>/releases/latest`.
- **Parsing**: It parses the JSON response to extract the `tag_name` (e.g., `v1.2`) and strips any prefixes/suffixes to get a clean semantic version string (e.g., `1.2`).
- **Comparison**: It fetches the local app version using `context.packageManager.getPackageInfo(context.packageName, 0).versionName`. If the GitHub tag version is greater than the local version, an update is available.
- **Downloading**: It searches the `assets` array in the JSON response for the appropriate `.apk` file. If found, it downloads the APK using `OkHttpClient` to the app's `cacheDir`.
- **Installing**: Once downloaded, it uses an Android `FileProvider` to launch an `ACTION_VIEW` intent with the `application/vnd.android.package-archive` MIME type, prompting the user to install the update.

*Crucial Note*: The `versionName` in your `build.gradle.kts` must always be manually updated before creating a new GitHub release, otherwise the app will enter a continuous update loop.

## 2. Dynamic UI Versioning
To ensure the settings UI correctly reflects the app's actual version (and doesn't mislead the user), always fetch the version dynamically in your UI (e.g., Jetpack Compose) rather than hardcoding it:
```kotlin
val currentVersionName = remember {
    try {
        context.packageManager.getPackageInfo(context.packageName, 0).versionName ?: "Unknown"
    } catch (e: Exception) {
        "Unknown"
    }
}
// Use currentVersionName in your UI
```

## 3. CI/CD GitHub Actions Setup (.github/workflows/android_build.yml)
To make updates seamless, GitHub Actions is used to automatically build, sign, and attach the release APKs whenever a new tag is pushed.

The workflow uses the `r0adkll/sign-android-release@v1` action. For this to work, you must define 4 specific Repository Secrets in your GitHub repository settings (Settings > Secrets and variables > Actions > New repository secret).

### The 4 Required GitHub Secrets:
1. **`SIGNING_KEY`**
   - **What it is**: The base64-encoded string of your Android Keystore file (`.jks` or `.keystore`).
   - **How to generate**: Run `base64 -i your_keystore.jks -o base64_keystore.txt` in your terminal, and copy the entire contents of the text file.

2. **`ALIAS`**
   - **What it is**: The key alias you specified when generating your Android Keystore.
   - **Content**: Just the plain text name (e.g., `upload_key` or `my_app_alias`).

3. **`KEY_PASSWORD`**
   - **What it is**: The password for the specific key alias inside the keystore.
   - **Content**: Plain text password.

4. **`KEYSTORE_PASSWORD`**
   - **What it is**: The password for the keystore file itself.
   - **Content**: Plain text password (often the same as `KEY_PASSWORD`, but depends on how you set it up).

When a new release tag is created, the CI/CD pipeline takes the unsigned release APK generated by `./gradlew assembleRelease`, signs it using these secrets, and uploads the signed APK as a release asset, which `AppUpdater.kt` will then find and download.
