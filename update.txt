# Over-The-Air (OTA) Update Logic & CI/CD Setup

This document details how the in-app update mechanism and the automated GitHub Actions CI/CD release process are implemented. You can use this guide to replicate this fully automated functionality in other Android app repositories.

## 1. AppUpdater.kt - Automated Tag-Based Updating
The core update logic is fully automated and tied to the exact Git commit SHA that triggered the GitHub Action. You never have to manually bump versions in `build.gradle.kts`.

### How it works:
- **API Call**: The app makes a GET request to the GitHub API: `https://api.github.com/repos/<OWNER>/<REPO>/releases/latest`.
- **Parsing**: It parses the JSON response to extract the `tag_name` (e.g., `v1.2-a63100c`) and normalizes it.
- **Comparison**: The app checks its internal build tag using `BuildConfig.GIT_TAG`.
  - If `BuildConfig.GIT_TAG` is exactly the same as the latest GitHub release tag, there is no update.
  - If the tags differ, an update is available!
  - (Local dev builds gracefully fallback to `"dev-build"` and won't trigger update prompts).
- **Downloading**: It searches the `assets` array in the JSON response for the appropriate `.apk` file. If found, it downloads the APK using `OkHttpClient` to the app's `cacheDir`.
- **Installing**: Once downloaded, it uses an Android `FileProvider` to launch an `ACTION_VIEW` intent to install the update.

## 2. Dynamic UI Versioning
The Settings UI directly displays `BuildConfig.GIT_TAG`. This means when a user looks at the version, they see exactly which commit the APK was built from (e.g., `v1.2-a63100c`), making debugging much easier.

## 3. CI/CD GitHub Actions Setup (.github/workflows/android_build.yml)
To make this tag automation work, the GitHub Action extracts the short commit SHA and injects it into the Gradle build process as an environment variable (`APP_VERSION_TAG`).

```yaml
    - name: Get Short SHA
      id: vars
      run: echo "sha_short=$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT

    - name: Build Release APKs
      env:
        APP_VERSION_TAG: "v1.2-${{ steps.vars.outputs.sha_short }}"
      run: ./gradlew :app:assembleRelease :our-music:assembleRelease
```

The app's `build.gradle.kts` captures this environment variable and writes it into the `BuildConfig` class:
```kotlin
val gitTag = System.getenv("APP_VERSION_TAG") ?: "dev-build"
buildConfigField("String", "GIT_TAG", "\"${gitTag}\"")
```

### The 4 Required GitHub Secrets:
To sign the automated release builds via the `r0adkll/sign-android-release@v1` action, you must define 4 specific Repository Secrets in your GitHub repository settings (Settings > Secrets and variables > Actions > New repository secret):

1. **`SIGNING_KEY`**
   - **What it is**: The base64-encoded string of your Android Keystore file (`.jks` or `.keystore`).
   - **How to generate**: Run `base64 -i your_keystore.jks -o base64_keystore.txt` in your terminal, and copy the entire contents of the text file.

2. **`ALIAS`**
   - **What it is**: The key alias you specified when generating your Android Keystore.
   - **Content**: Just the plain text name (e.g., `upload_key` or `my_app_alias`).

3. **`KEY_PASSWORD`**
   - **What it is**: The password for the specific key alias inside the keystore.
   - **Content**: Plain text password.

4. **`KEYSTORE_PASSWORD`**
   - **What it is**: The password for the keystore file itself.
   - **Content**: Plain text password (often the same as `KEY_PASSWORD`, but depends on how you set it up).
